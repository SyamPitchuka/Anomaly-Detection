What was built
--------------
- src/streaming/score_job.py: with --input kafka, every emitted window (train and test) also goes to
  data/latency_stream/source=smd/batch-<id>.parquet:
  entity_id, window_start, max_ingest_ts_ms, batch_max_ingest_ts_ms, emit_ts_ms, batch_id.
  There is one extra column you did not ask for: batch_max_ingest_ts_ms, the newest ingest time of the
  micro-batch that closed the window. It separates processing time from the watermark wait.
  The state carries the newest ingest time per open window (new state field open_ingest, so old
  checkpoints need --reset). LAYERS['scores'] and contracts/ are unchanged.
  New flags: --trigger (default 30 seconds, as before), --max-seconds, --idle-stop. --reset also wipes
  data/latency_stream. The query progress is logged to data/latency_stream/progress.jsonl.
- src/streaming/latency_report.py: per run, p50/p95/max of total (emit - newest ingest of the window),
  processing (emit - newest ingest of the batch), batch run time, watermark wait (measured and
  11 min / speed-up), and Kafka consumer lag over time. It writes docs/results/e2e_latency.md and .png.
- experiments/e2e_latency_runs.py: the run driver. Per run it recreates telemetry.smd, starts score_job
  and replay together, samples lag and free RAM every 5 s, and enforces the 25-minute cap and the 1 GB
  RAM floor.
- tests/test_latency_stream.py: 5 tests (ingest time per window across micro-batches with the state
  round-tripped, null without ingest_ts, parquet schema, percentiles, lag from the checkpoint).
- docs/results/e2e_latency.md, e2e_latency.png, e2e_latency_notes.md (analysis + how to repeat).

Main finding (look at this first)
---------------------------------
Every micro-batch takes about 11 s, even batch 0 with ZERO input rows (addBatch 11.2 s). At the same
time free RAM drops by about 1 GB once per batch, from a floor of about 1.8 GB. Both fit the Python
workers of applyInPandasWithState being restarted every batch and re-importing PyTorch and the models.
This is a hypothesis, not verified; e2e_latency_notes.md lists how to check it. Fixing it should remove
the 11 s floor and the RAM spike, after which the runs can be repeated with:
  python experiments/e2e_latency_runs.py
  python src/streaming/latency_report.py --notes docs/results/e2e_latency_notes.md
Other apps open during the runs: WSL vmmem 1.3 GB, Edge about 1.5 GB. Closing them would give headroom.
To reach p95 < 10 s the trigger also has to be well below 30 s (try --trigger "5 seconds").

Side observation, not investigated: in the first batches of the kafka runs, every emitted test window
was flagged (30/30, 6/6, 21/21; smoke run 36/36). The files run flags ~1% (63/5694). This may be the AE
adaptive threshold with a short score history at the start of a stream.
